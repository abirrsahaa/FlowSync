# FlowSync Development System — First-Principles Build Protocol

> Companion to `sytem_design.md`. That document is the **answer key** — the destination.
> This document is the **operating system for building it** — the process that guarantees:
> 1. **First principles** — you derive every design decision before reading it
> 2. **Full capability** — every technology is exercised to its depth, not its "hello world"
> 3. **End to end** — every feature is proven by a script, a drill, and a number — never "it seems to work"

---

## 1. The Prime Rule — the reference doc is an answer key, not a textbook

You never implement a section of `sytem_design.md` by reading it first. The order is always:

```
1. CLOSED BOOK: Given only the problem statement for the unit
   (e.g. "multiple users must see the same canvas in real time"),
   write your own design in derivations/<unit>.md:
     - What problem exists, precisely? What breaks without a solution?
     - What is the simplest thing that could work?
     - Where does the simple thing fail? At what scale/failure mode?
     - What are 2-3 candidate solutions and their tradeoffs?
     - Which do you pick and why?

2. OPEN BOOK: Now read the corresponding section of sytem_design.md.
   Diff your derivation against it. In the same file, add a
   "## Diff vs reference" section:
     - What did you get right? (this is now yours, permanently)
     - What did the reference do differently, and WHY is its choice
       better/worse? (if you can't articulate why, you haven't learned it)
     - What did you not know existed? → add to gaps.md

3. IMPLEMENT: Build it. Open book is fine here — implementation
   consults docs freely. Derivation is the closed-book part.
```

`gaps.md` is a running list of concepts you failed to derive. It is your real study list — far more honest than any generic prep guide, because it was generated by your own blind spots.

**Struggle budget:** during closed-book derivation, sit with a problem for at least 30 minutes before opening the reference. The discomfort is the mechanism. During implementation, no such rule — don't grind on syntax.

## 3. The Loop — seven gates for every unit of work

Every unit (a component, a feature, a pipeline) passes through seven gates, in order. A gate is passed only when its **artifact exists in the repo**.

```
Gate       Question it answers                 Artifact
─────      ─────────────────────────────       ─────────────────────────────
DERIVE     Could I have designed this?         derivations/<unit>.md (+ diff)
SPEC       What does "full capability" mean    specs/<unit>.md — capability
           for this unit?                      contract incl. failure behavior
BUILD      Does it exist?                      the code
PROVE      Does the FEATURE work end to end?   proofs/<unit>/ — a runnable
                                               script, not manual clicking
BREAK      Do I know how it fails?             drills/<unit>.md — drill run +
                                               observed behavior recorded
MEASURE    Is there a number on a dashboard?   Grafana panel + target met,
                                               screenshot/link in ledger
EXPLAIN    Can I teach it in 90 seconds?       explanations/<unit>.md —
                                               written closed-book
```

Gate rules:
- **PROVE is scripted.** "Open two tabs and drag a node" is a demo, not a proof. The proof is a script (k6, testcontainers, headless WS clients) that a stranger could run and get pass/fail. Manual demos are allowed *in addition*, never *instead*.
- **BREAK is mandatory, not optional hardening.** You do not understand a component you have never watched fail. Minimum one drill per unit from the catalog (Section 5).
- **EXPLAIN is closed-book and time-boxed.** Write the explanation without looking at code or docs. If you can't, the unit isn't done — you built it but didn't absorb it. This file doubles as your interview talking-point bank.
- Gates cannot be skipped, but they can be cheap. A small unit's SPEC might be five lines. The discipline is in never letting a gate silently not exist.

## 4. The Ledger — single source of truth for progress

`ledger.md` at repo root. One row per unit. A unit is DONE only when all seven cells link to an artifact.

```markdown
| Unit                       | DERIVE | SPEC | BUILD | PROVE | BREAK | MEASURE | EXPLAIN |
|----------------------------|--------|------|-------|-------|-------|---------|---------|
| tldraw custom shapes       | [d](…) | [s](…)| ✅   | [p](…)| [b](…)| [m](…)  | [e](…)  |
| WS→Kafka ingest path       |        |      |       |       |       |         |         |
| OT merge processor         |        |      |       |       |       |         |         |
```

Ledger rules:
- A cell is filled with a **link to the artifact**, never a bare ✅ (BUILD excepted — the code is the artifact).
- Review the ledger at the start of every session. The next action is always: leftmost empty cell of the topmost incomplete row. This kills "I'll just start something new" drift.
- If a unit sits half-done for two weeks, either finish it or delete the row and its code. No zombie units.

## 6. End-to-End Feature Proofs

Components passing gates isn't enough — **features** cross many components. Each E2E proof is a script under `proofs/e2e/`, runnable against a full local stack (Docker Compose) and later against EKS. These are the "every feature implemented end to end" guarantee.

```
ID      Feature slice                        Proof script does
──────  ─────────────────────────────        ─────────────────────────────────────
E2E-01  Solo full session                    Drives all 6 stages via API with a
                                             fixture design → asserts final report
                                             exists with 6 stage scores + gaps +
                                             next-problem rec.
E2E-02  Multiplayer convergence              2 headless WS clients, 500 random ops
                                             each, random jitter → assert identical
                                             final canvas state hash on both.
E2E-03  Replay determinism                   Replay session from offset 0 → assert
                                             reconstructed final state == live
                                             final state hash.
E2E-04  Challenge → arbitration              Seed a verdict, submit justification →
                                             assert structured ruling with ≥1
                                             citation referencing Stage-2 numbers,
                                             score adjusted, outcome persisted.
E2E-05  Presence lifecycle                   Client joins, heartbeats, killed →
                                             USER_OFFLINE broadcast within 15s.
E2E-06  Review streaming + node highlight    Trigger HLD review on fixture graph →
                                             assert annotation events carry valid
                                             node_ids that exist in the graph,
                                             tokens stream before is_final.
E2E-07  Deploy pipeline                      git push → CI → ECR → ArgoCD sync →
                                             PostSync smoke test green. Then push
                                             a broken image → auto-rollback fires.
E2E-08  Eval-gated prompt change             Prompt PR runs eval suite in CI;
                                             score in PR comment (mirrors the
                                             infracost pattern from Section 16).
```

E2E proofs run in CI where feasible (E2E-01…06 against Compose; E2E-07/08 are pipeline-native). A feature without an E2E row doesn't exist yet, whatever the components say.

## 7. Full-Capability Matrices

"Full capability" defined per technology: the checklist below is what it means to have *actually* used the thing deeply. Each item needs a pointer to where in FlowSync it's exercised — if an item has no natural home, that's fine, but the ones below all do. Track in `specs/capabilities.md`.

**Kafka** — producer EOS · Streams Processor API with RocksDB state store · interactive queries (resync, 24.7) · workspaceId partitioning + rebalance behavior (FD-17) · DLQ with alerting · replay from offset (E2E-03) · Avro + schema registry with a schema *evolution* (add a field mid-project deliberately) · MirrorMaker 2 (stretch, multi-region story)

**Redis** — all six patterns of Section 13, each with its drill · cluster mode failover (FD-16) · Lua atomicity proven under concurrency (FD-06) · keyspace notifications · memory analysis of presence/dedup keys at 10k users

**Java/WebFlux/Reactor** — STOMP @MessageMapping pipeline · Sinks.many() multicast + backpressure DROP (FD-05) · flatMap concurrency tuning with measured difference · StampedLock optimistic read vs RWMutex benchmark (JMH) · R2DBC · virtual threads where blocking is unavoidable · ZGC tuning with before/after GC pause panels

**Go** — goroutine-per-connection at 10k (FD-13) · buffered chan + select{default:drop} · sync.Map vs mutex-map benchmark · errgroup lifecycle with clean shutdown (drain on SIGTERM, proven during FD-14) · pprof flame graph captured under load and read

**Python async / FastAPI** — aiokafka consumer groups run as background tasks via FastAPI's lifespan (not a request/response server for the review path itself) · Pydantic models as the single schema source shared across Kafka messages, Redis stream events, and auto-generated OpenAPI docs · pytest-asyncio + httpx.AsyncClient testing · structured concurrency, no callback soup

**Agentic engineering** (the differentiator — hold to the highest bar) — six reviewer personas plus arbitration plus final-report, all thin subclasses of one Agent Harness `BaseAgent` (Section 19), with *measurably different* behavior (same input through two reviewers → different findings, captured) · schema-enforced structured output via Anthropic tool-use + Pydantic (24.2) with fallback path tested (FD-10) · eval harness as CI gate, invoking `BaseAgent` subclasses directly via `harness/eval_hook.py` with no network hop (24.1, FD-15, E2E-08) · adversarial eval cases run through `harness/injection_guard.py` (24.4, FD-09) · tiered model routing via `harness/model_router.py` with cost per session measured before/after (24.3) · prompt versioning via `harness/prompt_registry.py` with eval-score-by-version dashboard (24.11) · token-budget enforcement in the Lua limiter · streaming parse → UI annotation latency measured (node glows before prose completes)

**tldraw/frontend** — ShapeUtil per node type with typed props · store.listen() diff→op bridge · mergeRemoteChanges without echo loops · instance_presence cursors · setHintingShapes driven by stream events · toSvg() snapshot pipeline

**DevOps** — Terraform apply/destroy/apply reproducibility · IRSA end to end (zero static credentials, verified by grepping the cluster) · KEDA all three triggers observed actually scaling (screenshot pod counts during FD-13) · ArgoCD rollback both automatic (E2E-07) and via git revert · Trivy/OWASP failing a build on a real CVE once · preview environments per PR

**Observability** — trace_id from WS frame through Kafka headers to broadcast, queried in Tempo (one trace screenshot = the debugging story) · custom histograms with correct buckets · 5 dashboards live · alert rule that has actually fired once (trigger it deliberately) · logs↔traces correlation in Loki by trace_id

## 9. Cadence and Rituals

**Session ritual (every sitting):**
1. Open `ledger.md`. Next action = leftmost unfilled gate, topmost incomplete unit.
2. Work the gate. Commit its artifact.
3. Last 5 minutes: update ledger, append one line to `log.md` (date, what moved, what's blocked). This log is also your build-in-public content feed if you want one.

**Weekly review (30 min, non-negotiable):**
- Ledger: any unit stuck >2 weeks? Finish or delete.
- `gaps.md`: pick ONE gap, study it properly, write it up in `explanations/`.
- Re-run one previous drill cold. If you can't predict its outcome before running it, re-read your own drill notes — retention check.

**Demo discipline:** at every checkpoint completion, record a 2-3 minute screen capture of the deliverable working (the Section 21 deliverable + one drill). By CP10 you have ~11 clips that concatenate into a complete product demo — and each clip is a rehearsal of an interview answer.

**When stuck:** 30-minute struggle budget applies to *derivation* only. For implementation bugs, timebox 90 minutes then take help from any source — grinding on a Gradle error teaches nothing.
